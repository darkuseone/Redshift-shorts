# redshift-vision-critic

## Три шага (§7.3)

**Шаг 1 — дешёвая отбраковка без vision.** Метаданные, разрешение,
длительность, ориентация, лицензия, водяные знаки, дубли по pHash. Отсеивает
~50–60 %. Стоимость ≈ 0. Выполняется в P7 — там он экономит не только вызовы
модели, но и скачивания. Кандидатов набираем с запасом (Pexels + статья +
Википедия + сток): часть не пройдёт.

**Шаг 2 — mid-critic GLM.** Все прошедшие; для видео — 3 кадра. Оценивает:
что реально изображено, соответствие смыслу блока, качество, композицию под
9:16, наличие текста и логотипов, «стоковость». Возвращает `score 0.0–1.0` и
причину. **Gemini API не вызывать.**

**Шаг 3 — арбитраж Grok.** Только спорные / непонятные кадры:
* `score ∈ [0.45, 0.80]`, либо
* расхождение оценок кадров одного видео > 0.3.

**Лимит 3 вызова на ролик.** Решение арбитра финальное. Смысловой QC готового
ролика (P12) — тоже Grok (`vision.qc`), не Gemini.

## Пороги

`≥ 0.80` — принять (восемь из десяти), `< 0.45` — отклонить, между — шаг 3.

**Незакрытый слот идёт в генерацию (P9), а не заполняется слабым футажом.**
Это прямое требование §7.3, и его легко нарушить «из лучших побуждений».
Единственное исключение — исчерпанный лимит арбитража: тогда берётся лучший из
спорных и помечается `accept_fallback`.

## Статья, не сток «по теме»

Для evidence: `og:image` / json-ld со страницы `sources[].url`, плюс Wikipedia
REST, если источник — вики или у статьи есть title. Pexels остаётся в пуле.
Не подменять официальный кадр пресс-релиза абстрактным стоком.

## Что не оценивается повторно

Материал из локальной базы уже имеет оценку — платить за тот же кадр второй раз
нельзя (§7.2.1, идемпотентность §7.6).

## Мемы

В оценке релевантности B-roll **не участвуют** — у них отдельный пайплайн
(§5.8).
