# Готовый голос — второй входной артефакт двухфазного конвейера

Здесь лежит озвучка, под которую сгенерированы клипы ведущего:

```
assets/voice/<video_id>/voice_final.wav        # выход P3
assets/voice/<video_id>/speech_map.json        # выход P3
assets/voice/<video_id>/draft_plan.json        # выход P1
assets/voice/<video_id>/validated_script.json  # выход P0
```

## Зачем это в репозитории

Голос и клипы ведущего рождаются парой. Липсинк строится по конкретному куску
речи, и P6 отбраковывает клип, чей хронометраж разошёлся с этим куском больше
чем на 0.2 сек, — иначе рассинхрон видно на первом же слове.

Клипы с самого начала лежали в git, а голос — только в кэше Actions. Кэш
эфемерен: он не сохраняется на упавшей задаче (а фаза 1 падает всегда, это её
штатный исход) и вытесняется по объёму. Дважды кэш терялся, ElevenLabs
переозвучивал заново, границы фраз уезжали — и весь набор клипов шёл в брак.
Голос в кэше при клипах в git — это не оптимизация, а гарантированный развал
пары.

Поэтому голос хранится рядом с клипами. Четыре файла — около 5 МБ.

## Как это работает

Workflow раскладывает содержимое `assets/voice/<video_id>/` в `work/<video_id>/`
перед запуском конвейера. Дальше прогон идёт с `--from P4`: P4 (выравнивание),
P5 (монтажный план) и P6 (нарезка под аватара) детерминированны при одном и том
же голосе, поэтому клипы из `assets/avatar_clips/<video_id>/` сходятся с речью
кадр в кадр, а поиск футажа и рендер отрабатывают в том же прогоне.

Кэш прогонов при этом остаётся, но уже только как ускоритель: потеря кэша больше
не ломает сборку, а лишь заставляет заново искать футаж.

## Откуда взять

Первый прогон по новому сценарию идёт с нуля и озвучивает сам. Артефакт
`avatar-request` этого прогона несёт и заявку на клипы, и эти четыре файла —
их и нужно положить сюда, вместе с клипами, которые по заявке сгенерированы.
